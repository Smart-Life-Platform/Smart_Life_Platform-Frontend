## Загальний опис проєкту Reclaim.ai — Smart Life Platform

Smart Life Platform — веб-застосунок, що виконує роль персонального цифрового помічника. На відміну від звичайного чат-бота на базі LLM, продукт поєднує в собі функціонал планувальника, фінансового трекера та AI-асистента в межах єдиного dashboard, до якого користувач звертається щодня.

Концептуально продукт розташований на перетині Notion (структуроване планування та задачі), Google Calendar (події й розклад), персонального фінансового трекера (бюджет і покупки) та AI- асистента (персональні рекомендації на основі поведінки користувача), але має власну цілісну концепцію — усі дані користувача (задачі, фінанси, події, статистика) живуть в одному профілі та

впливають одне на одного через AI-рекомендації.

## Основні модулі системи

- Профіль користувача — реєстрація, авторизація, персональні налаштування.

- Планування дня/тижня та задачі — календар, список справ, пріоритизація.

- Бюджет і покупки — облік доходів/витрат, списки покупок.

- Події — особисті та заплановані події, нагадування.

- Статистика — аналітика активності користувача за модулями.

- AI-помічник — персональні рекомендації на основі даних з усіх модулів.

- Dashboard — єдиний екран, що об'єднує віджети всіх модулів.


## Загальний технологічний стек

- Frontend: React.js (деплой через Vercel)

- Backend: Django (Python)

- База даних: Supabase (PostgreSQL)

- Авторизація: Supabase Auth (вбудований механізм Supabase; RLS працює з токенами Supabase Auth, тому доступ до даних дійсно захищений на рівні бази)

- DevOps: Docker, CI/CD (GitHub Actions), деплой бекенду на staging (Hugging Face Spaces) та фронтенду (Vercel)

- AI: Gemini API (Google) — LLM-провайдер для AI-рекомендацій, виявлення аномалій та дайджестів (використовується безкоштовний тариф)

- Дизайн: Figma

## Принцип розподілу роботи

Роботу поділено на 5 приблизно рівних за обсягом технічних завдань: три — для програмістів (кожен веде свій модуль повним циклом: БД → бекенд → фронтенд → DevOps → AI-компонент), два — для дизайнерів (кожен відповідає за UI/UX двох-трьох модулів і частину спільних матеріалів — дизайн-системи або брендбуку). Такий розподіл дозволяє кожному учаснику мати завершену, самостійно демонстровану частину проєкту для захисту диплома, зберігаючи при цьому цілісність продукту.

## Програміст 1

## Модуль «Задачі та планування»

## 1. Вступ

Мета модуля — реалізувати повноцінну систему керування задачами та плануванням часу користувача: створення, категоризацію, пріоритизацію задач і їх відображення в календарі на день/тиждень, з інтеграцією AI-рекомендацій щодо пріоритетів.

## 2. Вимоги до функціоналу

## 2.1 Основні функції

- CRUD задач — створення, перегляд, редагування, видалення задач із полями: назва, опис, категорія, статус, пріоритет, дедлайн.

- Категорії задач — створення власних категорій із кольором/іконкою, прив'язка задачі до категорії.

- Статуси задач — керований набір статусів (наприклад: заплановано, у процесі, виконано, скасовано).


- Планування дня/тижня — API та UI для перегляду задач у розрізі дня/тижня, зв'язок задач із подіями календаря.

- Календар — відображення задач на сітці дня/тижня/місяця з можливістю перетягування (drag- and-drop) для зміни дати/часу.

## 2.2 Додаткові функції (рекомендовано додати)

- Підзадачі / чек-лист усередині задачі.

- Повторювані задачі (щодня/щотижня/щомісяця).

- Kanban-дошка як альтернативний вигляд списку задач (за статусами).

- Нагадування про дедлайни (push/email, реалізується разом із загальною системою нотифікацій).

- Шаблони задач для типових активностей.

- Тижнева статистика виконання (% завершених задач), що передається в модуль «Статистика».

## 3. Технічні вимоги

## 3.1 База даних (Supabase)

- tasks (id, user_id, title, description, category_id, status_id, priority, due_date, due_time, is_recurring, created_at, updated_at)

- task_categories (id, user_id, name, color, icon)

- task_status (id, name, order)

- task_subtasks (id, task_id, title, is_done) — для чек-листів

## 3.2 Бекенд (Django)

- REST API з повним CRUD для задач, категорій, статусів, підзадач.

- Ендпоінти для вибірки задач за діапазоном дат (день/тиждень/місяць).

- Логіка автоматичного перенесення протермінованих задач (опційно, за погодженням).

- Валідація вхідних даних і обробка помилок у єдиному форматі відповіді API.

## 3.3 Фронтенд (React.js)

- UI створення/редагування задачі (форма з валідацією полів).

- Компонент календаря з перемиканням вигляду День/Тиждень/Місяць.

- Kanban-вигляд списку задач.

- Фільтрація та сортування за категорією, статусом, пріоритетом.

- Інтеграція з dashboard (віджет «Задачі на сьогодні»).

## 4. Інтерфейс користувача — основні екрани

- 1. Список задач

- 2. Календар (день/тиждень/місяць)

- 3. Форма створення/редагування задачі

- 4. Kanban-дошка


5. Деталі задачі (підзадачі)

6. Налаштування категорій

## 5. Безпека

- Доступ до задач лише автентифікованого власника (Row Level Security у Supabase).

- Перевірка JWT-токена на кожному запиті до API.

- Валідація та санітизація введених даних на бекенді.

## 6. Тестування

- Юніт-тести бізнес-логіки (пріоритизація, повторювані задачі).

- Інтеграційні тести CRUD-ендпоінтів та вибірки за датами.

- E2E-тестування сценарію «створити → відредагувати → перенести в календарі → виконати задачу».

## 7. DevOps

- Налаштування CI/CD (GitHub Actions) для автотестів і збірки модуля.

- Тестовий деплой модуля на staging-середовище.

- Керування змінними середовища (.env) для підключення до Supabase.

## 8. AI-компонент

- Автоматичні рекомендації щодо пріоритизації задач на основі дедлайну, категорії та історії виконання.

- Підказка оптимального часу виконання задачі на основі завантаженості дня.

- Короткий тижневий інсайт («ви найпродуктивніші вранці» тощо).

## Критерії приймання (deliverables)

- Робочий модуль «Задачі та планування», інтегрований у спільний dashboard.

- Задокументоване API (Swagger/OpenAPI або аналог).

- Задачі та календар синхронізовані між собою в реальному часі.

- Модуль розгорнутий на staging і покритий базовими тестами.

## Програміст 2

Модуль «Бюджет і покупки»

## 1. Вступ


Мета модуля — реалізувати облік особистих фінансів (доходи/витрати) та керування списками покупок, з автоматичним підрахунком балансу, аналітикою за категоріями та персональними фінансовими порадами від AI.

## 2. Вимоги до функціоналу

## 2.1 Основні функції

- Облік доходів і витрат — додавання, редагування, видалення фінансових записів із сумою, категорією, датою, приміткою.

- Категорії витрат/доходів — стандартний набір + можливість створювати власні категорії.

- Списки покупок — створення списків, додавання/видалення позицій, позначення купленого (статус).

- Підрахунок балансу — автоматичний розрахунок балансу за день/тиждень/місяць, розбивка витрат за категоріями.

- Ліміти бюджету — встановлення місячного ліміту на категорію та відстеження прогресу витрачання.

## 2.2 Додаткові функції (рекомендовано додати)

- Сповіщення про перевищення бюджетного ліміту по категорії.

- Повторювані (регулярні) витрати — підписки, комунальні платежі.

- Експорт транзакцій у CSV/Excel.

- Спільні списки покупок (доступ кількох користувачів до одного списку) — опційно.

- Мультивалютність — опційно, якщо дозволяє час.

## 3. Технічні вимоги

## 3.1 База даних (Supabase)

- budget_records (id, user_id, type[income|expense], amount, category_id, date, description, is_recurring)

- budget_categories (id, user_id, name, icon, type, monthly_limit)

- shopping_lists (id, user_id, title, created_at)

- shopping_list_items (id, list_id, name, quantity, is_purchased)

## 3.2 Бекенд (Django)

- API для CRUD фінансових записів і категорій.

- Логіка підрахунку витрат/доходів і балансу за період.

- API для списків покупок (CRUD списків та позицій, зміна статусу «куплено»).

- Ендпоінт агрегованої статистики за категоріями (для графіків і для модуля «Статистика»).

## 3.3 Фронтенд (React.js)

- Форма введення доходу/витрати з вибором категорії.

- Список транзакцій із фільтрами (за датою, категорією, типом).


- Віджети для покупок (список + чекбокс статусу, лічильник позицій).

- Графіки витрат за категоріями (кругова/стовпчикова діаграма).

- Індикатори прогресу по бюджетних лімітах.

## 4. Інтерфейс користувача — основні екрани

- 1. Огляд бюджету (баланс, доходи/витрати)

- 2. Форма додавання доходу/витрати

- 3. Список транзакцій із фільтрами

- 4. Список покупок

- 5. Аналітика (графіки за категоріями)

- 6. Налаштування лімітів бюджету

## 5. Безпека

- Доступ до фінансових даних лише власника акаунту (RLS у Supabase).

- Валідація сум і дат на бекенді (захист від некоректних/негативних значень де це неприпустимо).

- Логування критичних операцій (видалення записів, зміна лімітів).

## 6. Тестування

- Юніт-тести логіки підрахунку балансу та лімітів.

- Інтеграційні тести API транзакцій і покупок.

- E2E-сценарій «додати витрату → перевірити оновлення балансу та графіка».

## 7. DevOps

- Оптимізація продуктивності — кешування агрегованих запитів (Redis або аналог).

- Моніторинг логів і помилок (наприклад, Sentry).

- Профілювання найважчих запитів (аналітика за період).

## 8. AI-компонент

- Персональні фінансові поради («зменшити витрати на категорію X на Y%»).

- Виявлення аномальних (нетипово великих) витрат.

- Прогноз залишку бюджету до кінця місяця на основі поточної динаміки витрат.

## Критерії приймання (deliverables)

- Робочий модуль «Бюджет і покупки», інтегрований у спільний dashboard.

- Коректний підрахунок балансу та коректна робота бюджетних лімітів.

- Аналітика за категоріями відображається графічно.

- Модуль розгорнутий на staging і покритий базовими тестами.


## Програміст 3

Модуль «Профіль, події та статистика»

## 1. Вступ

Мета модуля — реалізувати авторизацію та профіль користувача, керування подіями, збір і відображення статистики активності, а також головний Dashboard, що об'єднує віджети з усіх модулів платформи в єдиний екран.

## 2. Вимоги до функціоналу

## 2.1 Основні функції

- Авторизація/реєстрація — реєстрація, вхід, вихід, оновлення токена та відновлення пароля через Supabase Auth.

- Профіль користувача — перегляд і редагування особистих даних, аватар, налаштування (мова, часовий пояс, тема).

- Події — створення, редагування, видалення подій із датою, часом, місцем, категорією та нагадуванням.

- Статистика — збір і агрегація даних активності користувача (задачі, бюджет, події) для відображення трендів.

- Dashboard — головний екран із віджетами: профіль, задачі на сьогодні, бюджет, найближчі події, статистика, рекомендації AI.

## 2.2 Додаткові функції (рекомендовано додати)

- Вхід через соціальні мережі (Google OAuth).

- Налаштування сповіщень (які події/нагадування отримувати).

- Перемикання теми оформлення (світла/темна).

- Експорт статистики у PDF-звіт.

- Гейміфікація — базові досягнення/бейджі за активність (опційно).

## 3. Технічні вимоги

## 3.1 База даних (Supabase)

- profiles (user_id — посилання на auth.users.id у Supabase Auth, full_name, avatar_url, timezone, language, theme, created_at)

- events (id, user_id, title, description, date, time, location, category, reminder_at)

- statistics (id, user_id, metric, value, period_start, period_end)

## 3.2 Бекенд (Django)

- Інтеграція з Supabase Auth (реєстрація, вхід, оновлення токена, відновлення пароля); бекенд перевіряє JWT, виданий Supabase Auth, на кожному запиті.

- API для створення/редагування подій.


- API для збору статистики — агрегація даних із модулів задач і бюджету через внутрішні виклики/спільну БД.

- Ендпоінт зведених даних для dashboard (одним запитом — всі віджети).

## 3.3 Фронтенд (React.js)

- Екрани реєстрації/входу з валідацією форм.

- Dashboard із набором незалежних віджетів (профіль, статистика, події, задачі, бюджет).

- UI створення/редагування подій, календар подій.

- Сторінка профілю з редагуванням даних і налаштувань.

- Сторінка статистики з графіками активності.

## 4. Інтерфейс користувача — основні екрани

- 1. Реєстрація / Вхід

- 2. Dashboard (головний екран)

- 3. Профіль користувача

- 4. Календар подій

- 5. Форма створення події

- 6. Сторінка статистики

- 7. Налаштування акаунту

## 5. Безпека

- Хешування та зберігання паролів — на стороні Supabase Auth (бекенд не зберігає password_hash); безпечне зберігання і перевірка виданого Supabase JWT.

- Rate limiting на ендпоінтах авторизації (захист від брутфорсу).

- Налаштування CORS для дозволених доменів фронтенду.

- Можливість видалення акаунту та експорту особистих даних користувача.

## 6. Тестування

- Юніт-тести логіки авторизації та агрегації статистики.

- Інтеграційні тести API подій і статистики.

- E2E-сценарій «реєстрація → вхід → перегляд dashboard → створення події».

- Базове тестування безпеки (перевірка захисту ендпоінтів без токена).

## 7. DevOps

- Налаштування Docker-контейнерів для всіх сервісів платформи (docker-compose).

- Автоматичний деплой бекенду на Hugging Face Spaces та фронтенду на Vercel.

- Резервне копіювання бази даних.

## 8. AI-компонент


- Генерація персональних рекомендацій на основі зведеної статистики (продуктивність, витрати, активність).

- Формування короткого «дайджесту дня/тижня» для користувача на dashboard.

- Чат-інтерфейс AI-помічника — реалізація закріплена за цим модулем: бекенд-ендпоінт для запитів до Gemini API з передачею контексту користувача (задачі, бюджет, події) та фронтенд- віджет чату на dashboard.

## Критерії приймання (deliverables)

- Робочі авторизація, профіль, події та статистика.

- Dashboard, що коректно відображає дані з усіх трьох модулів в одному екрані.

- Розгорнута інфраструктура (Docker) для всього застосунку.

- Модуль покритий базовими тестами та розгорнутий на staging.

## Дизайнер 1

## Брендбук, дизайн-система та UI/UX авторизації, профілю, Dashboard і модуля «Задачі та планування»

Зона відповідальності: фундамент візуальної айдентики платформи, дизайн-система (UI Kit), UI/UX екранів авторизації, онбордингу, профілю користувача, Dashboard та модуля «Задачі та планування».

## 1. Брендбук та фірмовий стиль

## 1.1. Вступна частина

- Оформлення: титульна сторінка.

- Позиціонування: місія бренду та детальний портрет цільової аудиторії (ЦА).

- Неймінг (семантика та історія назви), слоган та його обґрунтування.

## 1.2. Логотип та правила використання

- Варіанти логотипа: основна та другорядні версії (вертикальний, горизонтальний, знак/емблема).

- Геометрія та побудова: модульна сітка, охоронні поля, мінімальні розміри.

- Кольорові версії: монохромна версія (позитив / негатив), правила використання на кольорових, фотографічних та складних фонах.

## 1.3. Константи фірмового стилю

- Палітра: основні та додаткові кольори (RGB, CMYK, HEX, Pantone).

- Типографіка: основний та акцентний шрифти, накреслення, таблиця знаків/Glyphs, демонстрація ритму через панграму.


- Графіка: стилеутворюючі елементи та фірмовий патерн.

## 1.4. Digital & Web

- Веб-ресурс.

- Основні принципи використання фірмового стилю в цифровому середовищі.

- Базові шаблони digital-комунікації.

## 2. Дизайн-система (UI Kit)

- Дизайнер 1 є основним відповідальним за створення спільного Component Kit у Figma. Дизайнер 2 бере участь у його розвитку та перевірці компонентів на екранах своїх модулів.

- Колірні токени: основні, акцентні, семантичні кольори (Success, Error, Warning, Info), підтримка Light та Dark тем.

- Типографіка: шрифтові пари, масштабована шкала заголовків і основного тексту, міжрядкові інтервали.

- Сітка та адаптивність: Spacing scale, Grid/Breakpoints для Desktop, Tablet та Mobile Web.

- Іконографія: єдина системна бібліотека ікон.

- Компоненти UI: кнопки, поля вводу, чекбокси/радіобатони, картки, модальні вікна, банери, badges/статуси, графіки та діаграми, елементи віджетів.

- Інтерактивні стани компонентів: Default, Hover, Active, Disabled, Focus, Error, Empty states.

## 3. Об'єкти дизайну

## 3.1. Авторизація, Онбординг та Профіль

- Реєстрація / Вхід / Відновлення доступу.

- Оптимізоване компонування інформації без перевантаження екрана.

- Варіанти Dashboard у світлій та темній темах.

## 3.3. Модуль «Задачі та планування»

- Список задач.

- Календар: день / тиждень / місяць.

- Kanban-дошка.

- Деталі задачі та підзадачі.

- Форма створення / редагування задачі.

- Дизайнер 1 відповідає за первинне UX-проєктування таких сценаріїв:

- Створення задачі → Планування тижня на Kanban/Календарі.

## 5. Презентаційні та рекламні матеріали

- Базовий digital-шаблон для комунікації бренду.

- Один із форматів рекламної продукції на основі фірмового стилю.

- Підготовка візуальних матеріалів для демонстрації бренд-системи на захисті.

## 6. Загальні вимоги до UI/UX

- Навігація та UX: мінімальна кількість дій для виконання ключових задач.

- Пропрацьовані інтерактивні стани.

- Критерії приймання — Дизайнер 1

- Готова частина брендбуку: позиціонування, неймінг, логотип, кольори, типографіка, графічна система та digital-принципи.

- Дизайн-система (Component Kit, Tokens, Styles) у спільному Figma-файлі.

- Hi-fi макети авторизації, онбордингу, профілю та Dashboard у світлій і темній темах.

- Hi-fi макети всіх основних екранів модуля «Задачі та планування».

- Wireframes і user flows для двох закріплених сценаріїв.

- Підготовлені презентаційні матеріали своєї частини роботи.

## Спільні вимоги команди

## Єдині для всіх учасників проєкту

## 1. Технологічний стек


- Frontend: React.js (деплой через Vercel).

- Backend: Django або ASP.NET (єдиний вибір для всієї команди).

- База даних: Supabase (PostgreSQL).

- Авторизація: JWT.

- DevOps: Docker, CI/CD (GitHub Actions), staging бекенду на Hugging Face Spaces, фронтенду — на Vercel.

- Дизайн: Figma (спільний файл із бібліотекою компонентів).

## 2. Процеси розробки

- Git-flow: гілки main, dev, feature/<назва-модуля>; злиття через Pull Request з рев'ю щонайменше одним учасником команди.

- Трекінг задач команди — Trello/Notion (дошка з усіма фічами трьох модулів).

- Щотижневі синхронізації для узгодження API-контрактів між модулями (особливо для dashboard і статистики, що залежать від даних інших модулів).

- Дизайн-хендофф: готові макети у Figma з Dev Mode для зручної передачі програмістам.

## 3. Орієнтовні етапи роботи

- Етап 1 — Дослідження та вайрфрейми: user flow, wireframes, структура БД усіх модулів.

- Етап 2 — Дизайн-система та hi-fi макети + налаштування бекенду й БД.

- Етап 3 — Розробка фронтенду, інтеграція з API кожного модуля.

- Етап 4 — Реалізація AI-компонентів та об'єднання модулів у спільний dashboard.

- Етап 5 — Тестування, DevOps (Docker, CI/CD, деплой на staging).

- Етап 6 — Полірування UI, підготовка презентаційних матеріалів і захист проєкту.

## 4. Критерії приймання проєкту в цілому

- Працездатний MVP Smart Life Platform з усіма основними модулями, інтегрованими в єдиний dashboard.

- Застосунок розгорнутий і доступний за посиланням на staging-середовищі.

- Наявна коротка технічна документація (опис API, структура БД, інструкція запуску).

- Готові презентаційні матеріали ( відео, проморолик) для захисту диплома.
